### 4.1 分表导出的列语义，规格与实现互相矛盾 ⚠️

这是当前最需要澄清的一处。两边说的不是一回事：

**规格**（`docs/superpowers/specs/2026-09-12-account-split-export-design.md`）明确要求：

> 不再为同一行横向追加多组"转存结果"列……原"分享链接"和"提取码"单元格在成功时直接替换为本次生成的最新值，**不新增"原链接/新链接"列，也不新增横向结果列**。

**实现**（`ReplacementWorkbookExportService.ExportSplitToDirectoryAsync`）实际做了两件事：

1. 在原列中就地替换（符合规格）；
2. **同时又在末尾追加了 4 列** `转存结果`、`分享链接`、`提取码`、`失败原因`（违反规格）。

```csharp
var layout = new ReplacementWorkbookLayout(
    definition.OriginalColumns.OrderBy(c => c.ColumnOrdinal).Select(c => c.Header)
        .Concat(["转存结果", "分享链接", "提取码", "失败原因"]));   // ← 规格禁止
```

**需要你决定**：以规格为准（去掉追加列），还是以实现为准（修订规格）？
在你决定之前，不要有人去"修"其中任何一边。

## 6. 已知缺陷与红灯（不要描述成"全绿"）

### 6.1 两个性能门禁长期未通过

| 用例 | 实测 | 阈值 |
|---|---|---|
| `PreparedStreamingWritesHandleTwoHundredThousandResources...` | 37.06 s | 20 s |
| `ShareWritesStreamSixHundredThousandOperations...` | 3 m 38.87 s | 未达标 |

均为耗时断言失败，功能断言通过。**从 2026-08-21 拖至今未处理。不得直接调高阈值掩盖。**

### 6.2 分表导出的具体代码问题（本轮审阅新发现，均未修复）

文件：`src/BaiduBatchTransfer.Application/Jobs/ReplacementWorkbookExportService.cs`

1. **每个账号全表重扫**：`StreamSplitRowsAsync` 对每个 (账号 × 成功/失败) 组合都完整分页遍历一遍整个批次投影，再在客户端过滤。N 个账号 = **2N 次全表扫描**。20 万行多账号批次下代价极高，且与 6.1 的性能红灯直接相关。
2. **流式被就地破坏**：拿到 `IAsyncEnumerable` 后立刻 `materialized.Add(row)` 全量灌进 `List` 再发布，规格要求的"不把整批载入内存"未达成。
3. **表头匹配过宽**：`Header.Contains("链接")` / `Contains("提取码")` 会命中**所有**含该词的原始列。源表若同时存在"分享链接"和"备用链接"，两列都会被新链接覆盖。
4. **失败原因泄漏英文枚举**：`outcome.StableErrorCode ?? outcome.TransferStatus` 把 `"Failed"` 这类英文状态直接写进中文"失败原因"列；同文件内已有 `MapTransferStatus`（`"Failed" => "转存失败"`）却未被调用。
5. **时间戳用 UTC 而非本地时间**：全部调用点为 `timeProvider.GetUtcNow()`，规格要求"时间戳使用本地时间"。中国区用户的文件名会差 8 小时。
6. **`BuildSplit` 的截断弱于 `Build`**：长账号名截断时既无 `Build` 里的 SHA256 短哈希后缀（**两个不同长账号名可能撞成同一文件名**），也无代理对保护（`basis[..max]` 可能劈开一个代理对产生乱码）。规格要求的"同秒重名追加短序号"亦未实现。

### 6.3 测试覆盖不实

功能分支交接称 `ReplacementWorkbookExportTests` 通过 34 项，但其中**只有 2 项**涉及分表导出（一项文件名、一项单一 happy path）。上述 6.2 的六个问题**无任何测试覆盖**。

- 真实 `.xlsx` 读回测试未补齐，现有导出测试靠 writer/publisher 捕获行验证。
- `ExportSplitToDirectoryAsync` 尚未接入结果页"另存结果表格"按钮的完整 UI 流程。

## 8. 安全与操作边界（强制）

- **不泄露、不写日志**：Cookie、提取码、分享链接、账号 ID、百度用户 ID、完整响应正文、二维码。
- 真实百度操作**只能**使用用户明确提供的测试账号与无敏感内容链接。
- 任何"已完成/已通过"的结论**必须**附实际命令与输出；拿不出证据就写"未验证"。
- 证据不明确时，保持 `NotValidated` 与 `UnavailableAdapterAvailability`，**不得按文件名、目录、时间或 UI 成功文字猜测**。
- 不读取浏览器 Cookie、密码、本地存储或 Profile 文件；不要求用户手工复制 Cookie。
- Chrome/Edge 的登录态**不会**自动进入桌面应用的 WebView2。最终验收必须在应用自己的登录窗口重新扫码。
- 未经用户明确指示，**不合并、不推送、不建 PR、不连接任何服务器/staging/生产**。

## 9. 流程改进（本轮根因）

本轮暴露的根因不是"文档写得不够细"（旧交接 329 行，足够细），而是**没有单一事实来源**：读着 8 月的交接、在缺代码的分支上、规划了一个当天已完成的功能。

约定如下：

1. **主干只有一条**，功能分支存活不超过 3 天。
2. **交接文件只有一份**，且与代码同分支存放——代码在哪，交接就在哪。
3. 交接文件**重写，不打补丁**。旧版归档到 `docs/archive/` 并加作废横幅，不在原文里叠加"以下内容已过时"。
4. 任何计划文档必须声明其**基准分支与基准 commit**，否则视为无效。
