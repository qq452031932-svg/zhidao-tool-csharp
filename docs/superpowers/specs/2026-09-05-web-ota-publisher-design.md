# SuperPan 网页 OTA 发布后台设计

**状态：** 用户已确认产品方向，等待规格审查后进入实施计划。

## 目标与范围

在现有 `ota.fanfh.cn` 独立静态 OTA 站点上增加一个仅供管理员使用的网页发布后台。以后发布者无需 SSH 或打开宝塔，只需登录 `https://ota.fanfh.cn/admin/`，上传由本机发布脚本生成的完整 OTA ZIP，查看校验结果并确认发布。

本后台只管理 SuperPan 的 `win-x64-stable` 渠道，不提供通用网盘、文件管理器、在线构建、服务器端代码签名、多管理员、权限角色或第三方存储。本次继续保持 `f.fanfh.cn` 的目录、应用、数据库和虚拟主机配置不变。

## 已确认的产品决定

- 管理后台使用单一管理员账号和密码，不启用两步验证。
- 上传对象是本机发布脚本生成的完整 OTA 发布包 ZIP，不接受单独 EXE。
- 上传后先自动校验并展示结果，管理员再次点击“确认发布”才会切换线上版本。
- 只保留当前版本在内最近 3 个已发布版本，并支持一键回滚。
- 不购买商业代码签名证书。发布者在自己的 Windows 电脑上生成并保管一套固定的自签名代码签名证书；用户首次安装时手动信任公开 `.cer`。
- 后台只有一个正式更新渠道，不再区分测试渠道和正式渠道；每个发布包都必须由固定自签名密钥签署。
- 后台部署时生成一次性初始管理员密码，首次登录强制修改。

## 架构与隔离

现有 Nginx 继续直接提供 `/www/wwwroot/ota.fanfh.cn/releases/win-x64/stable/` 下的静态更新文件。新增发布后台作为独立、最小权限的本机服务运行：

- 后台只监听 `127.0.0.1` 的专用端口，不向公网开放内部端口。
- Nginx 仅将 `/admin/` 和对应 API 转发到后台；现有 `/health`、ACME 和静态 OTA 下载路径保持独立。
- 后台使用独立 Linux 用户、独立 systemd 服务、独立配置与数据目录，无权读取 `f.fanfh.cn` 的站点根、数据库或应用配置。
- 建议路径：程序 `/opt/superpan-ota-admin`，状态 `/var/lib/superpan-ota-admin`，配置 `/etc/superpan-ota-admin`，日志由 journald 和独立审计表保存。
- 静态 OTA 下载不经过后台进程；后台停止、升级或崩溃时，已经发布的客户端更新下载不受影响。

后台采用可在 CentOS 7 上运行的单一自包含服务。实施计划必须先做目标机兼容性探针，再锁定运行时；不得依赖或升级现有业务站点使用的 PHP、数据库或运行时。

## 管理界面

后台保持单页、低操作成本，只包含以下区域：

1. 登录：管理员账号、密码、首次登录改密。
2. 当前版本：版本号、发布时间、更新说明、资产数量、发布状态。
3. 上传发布：选择 ZIP、填写更新说明、上传进度。
4. 校验确认：逐项显示包 ID、渠道、版本、签名、文件清单、哈希、引用关系和空间检查；只有全部通过时显示“确认发布”。
5. 版本历史：最近 3 个版本、发布时间、操作者、更新说明、资产摘要和“回滚到此版本”。

页面不会暴露服务器路径、命令、私钥、完整异常堆栈或任意文件浏览能力。

## 身份验证与会话

- 管理员用户名固定，密码使用 Argon2id 和每用户随机 salt 保存，不保存明文或可逆密文。
- 首次部署生成高强度随机临时密码，仅显示一次；首次成功登录必须更换密码后才能上传或发布。
- 会话 Cookie 必须设置 `Secure`、`HttpOnly`、`SameSite=Strict` 和受限 Path；会话有固定最长寿命和空闲过期时间。
- 所有改变状态的请求必须校验 CSRF token、同源 `Origin`/`Referer` 和当前会话。
- 登录失败按来源与账号共同限速，连续失败触发短时锁定；日志只记录时间、结果和脱敏来源，不记录密码或 Cookie。
- 修改密码会撤销除当前改密响应外的全部既有会话；服务重启后旧会话不得自动恢复为有效。

## 自签名发布信任模型

自签名证书的私钥只存在于发布者的 Windows 电脑，不上传服务器、不写入仓库。公开证书或其公钥可部署到服务器，并在后台配置中固定 SHA-256 指纹。

本机发布脚本负责：

1. 用固定证书对 Windows 可执行资产执行 Authenticode SHA-256 签名和时间戳（时间戳服务可用时）。
2. 生成完整 `upload-manifest.sha256`，精确覆盖发布 ZIP 中除签名文件本身外的全部允许资产。
3. 使用同一固定私钥对 manifest 生成独立的 SHA-256 数字签名文件。
4. 在打包前重新验证 Authenticode、manifest 签名、哈希和文件集合。

服务器不执行签名，只验证：manifest 数字签名来自固定公钥、固定公钥指纹与配置一致、manifest 精确覆盖 ZIP 中的允许资产、每个资产的哈希与清单一致。没有签名、签名不匹配、使用另一张证书或只有 Authenticode 而没有签名 manifest 的 ZIP 一律拒绝。

用户首次安装时导入公开 `.cer` 是受控分发的信任步骤。自签名不能建立公共 CA 或 SmartScreen 信誉，因此界面和说明不得承诺完全消除 Windows 下载/信誉提示。

## 上传包契约与校验门禁

ZIP 顶层只允许当前生产包 ID `SuperPan.BaiduBatchTransfer`、渠道 `win-x64-stable` 所需的 release JSON、asset catalog、`RELEASES-win-x64-stable`、Full/Delta nupkg、固定 Setup/Portable、`upload-manifest.sha256` 及其签名文件。Acceptance 包、其他渠道、目录项、符号链接、未知文件、重复名、大小写碰撞和嵌套路径全部拒绝。

上传采用流式写入随机命名暂存文件，并执行压缩体积、解压总体积、单文件大小、条目数量和压缩比上限。解压只能写入由后台创建的独立暂存目录，所有规范化路径必须仍位于该目录内。磁盘剩余空间不足时在解压前拒绝。

门禁按 fail-closed 顺序执行：

1. ZIP 结构与资源上限。
2. 允许文件集合及名称规范化。
3. 固定发布公钥与 manifest 数字签名。
4. manifest 覆盖关系、每个文件大小和 SHA-256。
5. release JSON 的包 ID、渠道、版本、文件名、类型、大小和哈希引用。
6. asset catalog 与已验证资产的反向关联。
7. RELEASES 的 SHA-1、大小、文件名和 Full 集合。
8. 版本必须严格高于当前线上版本，且历史中不存在同版本。
9. 发布所需磁盘空间与服务当前状态。

上传完成只产生一条有过期时间的“已验证候选”，不改变线上 feed。候选记录绑定上传文件指纹、管理员会话和校验结果；确认发布前重新读取并复核候选指纹，防止暂存文件被替换。失败或过期候选可安全删除，不影响当前版本。

## 原子发布与恢复

后台使用数据库事务与进程级排他锁保证同一时间只有一个上传确认、发布或回滚操作。所有不可变资产先复制到稳定目录中的唯一版本文件名，并在服务器端重新计算哈希。元数据写入同一文件系统的临时文件并 `fsync`，release JSON 最后通过原子重命名替换，作为发布的唯一提交点。

发布前保存当前元数据快照和所引用资产集合。若在 release JSON 提交前失败，删除未引用临时文件并保留当前版本；若提交后日志事务未完成，服务启动恢复流程根据线上 release JSON 和磁盘哈希重建最终发布记录，不能猜测性地再次发布。

上传、确认和回滚响应都使用幂等操作 ID。浏览器超时或重复点击只返回同一操作的最终状态，不执行第二次切换。

## 版本保留与回滚

- 保存当前版本和之前两个已发布版本，共 3 个完整可恢复快照。
- 只有新版本成功提交并完成审计后，才清理第 4 个及更旧快照。
- 清理资产前必须证明它不再被当前 feed 或保留的三个快照引用；无法证明时保留文件并记录清理失败，不影响发布结果。
- 回滚需要重新输入当前管理员密码并二次确认目标版本。
- 回滚只原子恢复目标版本的元数据快照和引用，不重新签名、不修改资产。
- 回滚不会让已经升级的客户端自动降级。发现坏版本后，回滚用于阻止尚未升级的客户端继续获得坏版本；已升级客户端必须通过发布版本号更高的修复版恢复。

## 数据与审计

独立 SQLite 数据库至少记录：管理员密码哈希与改密状态、发布版本、候选上传、发布/回滚操作、资产引用和审计事件。数据库启用约束和事务，发布状态只能按定义的状态机前进。

审计事件记录登录结果、上传开始/完成、每项门禁结果、确认发布、发布失败、回滚和清理结果。不得记录密码、Cookie、私钥、完整服务器绝对路径或发布包中的敏感内容。审计记录不可通过网页删除。

## 错误处理

- 用户可纠正的错误显示简短中文原因，例如“版本号不是递增”“签名证书不匹配”“文件哈希错误”。
- 服务内部错误返回统一操作编号，详细信息只进入服务日志。
- 上传断开、浏览器关闭或服务重启不会发布候选；过期暂存由定时清理任务删除。
- 发布或回滚任一步骤无法证明结果时，管理界面显示“操作失败”，后台进入只读保护状态；完成磁盘与数据库一致性恢复前禁止新的发布动作。
- 后台故障不得修改 Nginx、证书续期配置或现有静态文件缓存规则。

## 部署与升级

部署新增独立 systemd unit、最小权限用户、数据目录和 Nginx `/admin/` 反向代理。Nginx 变更先备份、`nginx -t`，成功才 reload；随后同时验证管理后台、静态 OTA、证书和 `f.fanfh.cn` 基线。

后台自身升级采用独立二进制与配置备份，不通过它管理的 OTA 渠道自更新。失败时恢复上一后台二进制和 Nginx 配置；已发布静态 feed 不回滚、不删除。

## 验收标准

自动测试至少覆盖：

- 登录、首次改密、密码哈希、会话过期、CSRF、登录限速和会话撤销。
- 正常 ZIP、错误包 ID/渠道/版本、Acceptance、额外/缺失文件、大小写碰撞、路径穿越、符号链接、压缩炸弹和磁盘不足。
- 错误 manifest 签名、错误公钥、错误哈希、未覆盖资产及被替换候选。
- release JSON、asset catalog、RELEASES 和 manifest 的双向引用闭包。
- 重复版本、并发确认、重复请求、发布各提交点故障与重启恢复。
- 最近 3 版保留、共享资产保护、清理失败和回滚。
- 已升级客户端不会被错误描述为自动降级。

服务器验收必须使用隔离测试目录先完成真实上传、确认、失败注入和回滚，再接入稳定目录。最终验证 `/admin/` 登录与发布流程、OTA 静态下载和缓存头、HTTPS 证书、自动续期，以及 `f.fanfh.cn` 配置哈希、证书和页面响应均未变化。

## 非目标与后续事项

- 不购买或集成商业代码签名服务。
- 不在服务器保存自签名私钥或为上传包执行签名。
- 不实现多管理员、审批流、灰度百分比、客户端强制降级、通用文件管理或云存储同步。
- 后续若改用公共 CA/云签名，只替换固定发布证书和本机签名步骤；网页发布、校验、历史与回滚模型不需要重做。
